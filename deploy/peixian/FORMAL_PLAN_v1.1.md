# 1. 项目定位与正式版目标

## 1.1 业务与技术方向

沛县项目继续使用现有控制台分支，不以通用 SaaS 平台为本轮目标，不重新引入 Dify 或可视化工作流引擎。

采用以下分工：

| 层次 | 职责 | 不应承担的职责 |
|---|---|---|
| OpenCode Agent | 理解需求、按 Skill 选择工具、提出补充问题、整理结果 | 自行授予权限、任意访问业务系统、认定正式业务结论 |
| 官方业务 Skill | 描述处理方法、参数要求、业务步骤及输出规范 | 替代数据库约束、访问控制、审批或任务状态机 |
| 业务插件 Tool | 用明确合同调用查询、校验、计算、导入、报告等能力 | 暴露任意 URL、任意 SQL、通用 Shell 或高权限总密钥 |
| 控制层 | 身份、资料范围、任务记录、版本绑定、结果入口和审计 | 直接承担所有重型计算，或把所有账号目录开放给 Agent |
| 业务数据服务 | 结构化入库、确定性查询计算、结果集保存及来源关联 | 依赖模型生成文字决定授权和计算正确性 |
| 运维层 | 部署、资源限制、监控、备份、恢复和版本发布 | 让普通业务代码获得宿主 Docker 管理权限 |

业务功能可以逐项封装成官方 Skill，并复用相应插件。涉及敏感个人资料的业务，必须在批准的用途和数据范围内执行；本方案不设计无边界的数据扩线、自动处置或不经复核的事实认定机制。

## 1.2 P0 完成标准

P0 指接入真实业务数据前必须具备的能力：

- **权限可控：** 每次读取、计算和导出都受服务端身份、资料范围和操作许可约束。
- **任务可靠：** 已接收任务有持久化记录；重复提交、失败、重启和取消有明确语义。
- **结果可核对：** 区分原始数据、程序计算和模型解释，保存来源与人工复核记录。
- **故障可恢复：** 关键故障能被发现，备份经过独立恢复演练，升级失败有处置路径。

页面能打开、模型能回答、接口返回 202、容器显示健康，均不能单独证明 P0 完成。

## 1.3 建设方式

采用“模块化单体 + 必要的独立执行服务”。九个 P0 项目不等于九个微服务。

先复用现有 FastAPI、SolidJS、Docker 和 OpenCode 托管模式。业务模块优先在控制层中明确分层；需要独立凭据、网络或资源限制的接口代理、解析进程和业务 Worker，再独立部署。

5. 保留不完整文件解析不能被静默当全文提交给模型的规则。

# 3. 目标架构与关键技术决策

## 3.1 目标架构

```text
业务浏览器
    │ HTTPS
    ▼
正式访问入口 / 反向代理
    │
    ▼
沛县控制层 Control API
    ├── 身份与资料范围
    ├── 官方 Skill / 插件发布与授权
    ├── 业务 Run、审批、结果与审计
    └── 文件与数据集入口
             │
             ▼
      账号 Gateway / OpenCode Adapter
             │
             ▼
      隔离 OpenCode Runtime
        ├── Model Relay ──→ 已批准模型服务
        └── 已审核业务插件
                      │
                      ▼
                受控业务接口代理
                身份映射 / 权限 / 凭据注入
                参数校验 / 限流 / 审计
                      │
                      ▼
                业务数据服务
                导入 / 查询 / 计算 / 报告
                      │
                      ▼
            业务数据库 / 结果集 / 文件存储

独立职责：
  宿主 Worker：仅管理账号运行环境，持有受控 Docker 权限。
  业务 Worker：处理后台业务任务，不持有 Docker 权限。
  运维组件：监控、日志、备份、恢复和发布校验。
```

## 3.2 保留与新增

| 项目 | 首期决策 |
|---|---|
| 前端、控制层技术栈 | 保留 SolidJS 与 FastAPI，不为更换技术栈而重写 |
| OpenCode | 保留经过验证的内核基线，业务逻辑尽量不进入内核 |
| 数据库 | 不强制重构 OpenCode 会话库；新增业务数据、任务和结果独立建模 |
| 后台队列 | 先实现持久化任务、租约和恢复语义；数据库队列或成熟组件均可，不强制引入 Redis |
| 部署方式 | 首期可继续 Compose；是否需要高可用由甲方可用性要求决定 |
| Agent 组合 | 先使用一个专用业务 Agent 和多个官方 Skill，不默认建设复杂多 Agent 系统 |
| 文件存储 | 独立可管理的目录/卷即可起步；对象存储按规模和共享需求引入 |
| 框架分支能力 | 不假定 `codex/agent-framework` 的能力已存在于本分支 |

## 3.3 首期并发约束

建议 P0 初期对同一账号正式任务采用串行准入，减少共享运行环境中的并发配置与文件竞争；这是实施简化，不是权限边界。

不得在每次任务启动时改写共享 `opencode.json` 或共享环境变量来切换任务权限。任务上下文必须绑定独立 Run 和 Session，并在工具入口校验。后续开启并发前，补齐跨任务目录、事件和身份隔离测试。

不同案件/资料域必须使用新的会话上下文。需要文件系统级硬隔离时，应按资料域或任务分配独立运行环境和挂载，不得仅依赖提示词、目录命名或 Session ID。

# 5. P0-01：生产部署与网络安全

## 5.1 修改内容

### 生产配置与入口

- 新增独立生产部署覆盖文件，不覆盖开发配置或旧验收配置。
- 配置正式 HTTPS 入口、证书更新、精确 Origin、Secure Cookie 和必要的安全响应头。
- 明确反向代理可信范围，避免客户端伪造转发头影响身份、限流和审计。
- 保持 Agent、Gateway、Relay、数据库及 Worker 内部接口不面向普通业务用户开放。
- 配置上传上限、请求超时、流式连接策略和错误提示；验证反向代理不会截断正常 SSE。
- 运维接口使用独立的访问控制，不与普通业务入口混同。

### 环境与宿主

- 开发、测试、生产采用独立数据库、目录、密钥、模型配置和数据。
- 使用专用宿主服务账号，交付可直接安装的服务单元及启停检查脚本。
- 明确补丁维护、系统时间同步、受控运维入口及安装依赖来源。
- 运行时禁止临时联网安装插件或依赖；离线交付需准备与目标架构匹配的镜像和依赖。
- 保留现有非 root、只读根文件系统、能力裁剪、PID 和内存限制。[S04][S11]

### 网络与数据流向

- Agent 通过固定 Model Relay 调用已批准模型。
- 插件通过受控业务接口代理调用已批准数据服务。
- 将允许的目标服务、协议、端口、证书校验方式和访问用途形成清单。
- 在甲方明确数据分类、是否涉密、网络归属和适用安全要求前，不把外部模型连通当作真实资料发送许可。
- 模型的标题、摘要、上下文压缩等辅助请求同样受数据出口策略约束。

## 5.2 修改位置

现有：`deploy/peixian/compose.console.yaml`、`console-runtime.py`、`console-worker.py`、控制层认证配置。

建议新增：`compose.production.yaml`、反向代理配置、`systemd/`、生产预检查和安装脚本。

## 5.3 验收

- 全新目标服务器可以根据交付材料完成部署和版本核验。
- 服务器重启后组件按正确顺序恢复，Worker 离线能够告警。
- 普通用户不能访问内部接口或绕过代理直连运行环境。
- 未批准网络目标被拒绝，模型/业务凭据不进入普通日志、镜像或源码。

# 6. P0-02：身份、权限与业务资料范围

## 6.1 权限模型

本项目平台角色已经确定为三类，不再新增独立“业务审核员”“安全审计员”或“系统运维员”应用角色。宿主运维身份属于部署边界，不等于应用角色。资料域成员与访问范围仍作为资源授权维度，不能用平台角色替代。

| 平台角色 | 标识 | 已确定的职责 | 明确限制 |
|---|---|---|---|
| 超级管理员 | `super_admin` | 管理普通用户与管理员账号；管理模型；独占平台插件发布、版本配置、上架下架和用户授权；管理技能模板；部门公共 Skill 的唯一审核发布、授权和下架角色；独立空间维护与任务查看；只读脱敏管理审计 | 不通过普通用户接口读取私有业务内容；普通账号编辑接口不能修改任何超级管理员；不提供角色升降级 |
| 管理员 | `admin` | 管理全部普通用户的创建、启用、停用和密码重置；管理模型配置、连接测试、默认与启停、模型授权；查看只读脱敏管理操作记录 | 不能管理管理员或超级管理员，不能授予插件权限，不能管理平台插件与模板，不能修改部门组织或归属，不能独立暂停/恢复/重试/应用空间或查看环境任务 |
| 普通用户 | `user` | 自己的对话、文件、个人 Skill、已授权插件个人配置、个人密码和程序令牌 | 不管理平台模型、插件目录、账号、公共模板和审计；不能自行上传任意插件包 |

两个管理角色均没有 Agent/Gateway/Relay、业务 HOME/workspace/files 卷或普通用户运行名额，主导航只提供管理中心和个人设置。普通用户保留个人 Skill 的创建、编辑、导入、启停、回退，以及已授权插件的个人配置、启停和允许版本切换。

管理员对普通用户的业务管理可以产生必要后台环境任务：创建用户自动开通，停用自动排队暂停，模型或授权变更自动排队应用。这些副作用不授予管理员独立运行环境维护接口。普通用户从停用变为启用（active: false → true）时，服务端在同一事务内检查并预留容量、排入 resume，随后由执行器恢复原环境；管理员可通过“启用账号”完成这一业务动作，无需独立 runtime 权限。若停用引发的 pause 尚未完成，或没有可用名额，返回 409 并回滚本次启用，账号继续保持停用；待暂停完成或释放名额后再试。已经 active、只是被超级管理员手动暂停空间的用户，不会因修改其他设置或重复启用而自动恢复，仍须超级管理员“恢复空间”。

“唯一审核主体”指只有 `super_admin` 角色有权审核部门公共 Skill，不表示新增若干审核角色，也不表示本次完成了审核系统。公共 Skill 的完整状态机、版本合同、申请记录及发布授权在批次 D 实现；本次仅将既有模板管理收归超级管理员。

在平台角色允许该类操作的前提下，正式业务资料访问按以下组合决定：

```text
允许操作 = 用户/服务身份有效
        ∩ 当前资料域成员关系有效
        ∩ 资源归属与访问范围匹配
        ∩ 任务允许的工具与操作匹配
        ∩ 必要审批仍有效
```

只读查询不等于无需限制。批量读取和导出也需要按敏感性、用途及范围制定策略。

## 6.2 必须实现的后端校验

- 先验证 `super_admin/admin/user` 平台角色与具体操作权限，再验证目标账号类型及资源归属；前端根据服务端能力显示入口，不以隐藏按钮替代后端拒绝。
- 管理员可管理的用户范围是全部普通用户，不按其创建者缩小，也不引入部门管理权限。
- 用户创建接口默认创建 `user`；只有超级管理员能显式创建 `admin`。所有编辑接口拒绝修改 `role`，不得借普通账号操作增建或变更 `super_admin`。
- 任务、会话、文件、数据集、结果、报告和审批全部建立服务端归属关系。
- `scope_id`、`dataset_id`、`file_id`、`run_id` 只用于定位资源，不构成授权。
- 插件调用通过受信代码注入调用身份，业务代理根据运行环境、会话和任务映射校验，不能信任模型参数中的用户 ID。
- 使用任务级受限凭据或服务端映射时，限制有效期、目标服务、可用工具及资料范围；必要时校验撤销状态。
- 原生文件工具、插件文件接口、报告下载、会话历史和 SSE 事件使用一致的数据范围规则。
- 正式模式默认禁用无法执行资料范围校验的直接文件读取能力，使用受控文件工具替代。

## 6.3 审批与权限撤销

部门公共 Skill 的审核发布、授权与下架只允许超级管理员；管理员与普通用户均不得调用该管理入口。个人 Skill 不因该规定失去现有编辑与使用能力，模板复制也不等于已完成正式公共 Skill 审核。

任务中的高风险操作审批仍需单独的审批合同，不能把公共 Skill 审核权限自动扩展为任意业务数据审批。审批记录应绑定：审批人、任务、操作类型、规范化参数摘要、数据范围、有效期及是否已消费。参数或范围改变后重新审批。

账号停用、资料域移除或工具撤权后，新访问必须拒绝。已提交的下游任务单独判断能否取消，并保留明确状态。

不得通过在 Skill 中写“必须审批”来替代后端校验，也不得将对话中任意一条“同意”直接视为通用授权。

## 6.4 信任边界

平台插件是超级管理员批准的可执行代码，不能把同进程插件视为独立安全沙箱。审核发布和最小运行权限必须同时存在；若引入不受信第三方代码，需另行建设进程/容器隔离。

应用角色分离不意味着拥有宿主、数据库或密钥权限的运维人员在技术上完全无法接触数据。此类高权限操作需要独立审批、受控运维和审计，不能以“管理员 API 不显示资料”代替完整保障。

## 6.5 修改位置与交付

- 现有 `control/app.py` 的认证依赖逐步抽到统一安全模块。
- 新增 `control/business/security.py`、资料域及成员模型。
- 工具代理、会话访问、文件下载和结果接口共同接入策略。
- 交付三角色权限矩阵、能力响应、数据归属规则、审批合同和直接 API 越权回归用例。
- 控制库显式 schema 版本推进到 2：旧 schema=0 的旧 `admin` 一次性迁为 `super_admin`，保留 UID、账号名与密码哈希，增加 `auth_version` 并撤销旧认证；重复启动不把新建 `admin` 提权。
- 全新安装保留初始化账号名 `admin`，其角色为 `super_admin`，不分配业务环境。角色迁移只处理身份及认证，不修改已有普通用户卷和会话。
- 先进行角色兼容预检查与控制库备份，再执行迁移；拒绝不兼容旧镜像打开新 schema。具体运行命令以本分支受控脚本及 ROLES.md 为准，本方案不把文档修改当成迁移成功。

## 6.6 验收

跨账号、同账号跨资料域、伪造资源 ID、直接调用 API、旧会话访问、旧下载链接和撤权后调用均按策略拒绝；角色职责不因前端隐藏而成为唯一保障。另以三种角色直接调用所有管理路由，验证插件授权、模板、角色变更和环境维护禁区；核对两个管理角色均无业务运行环境。

# 7. P0-03：业务任务持久化与可靠执行

## 7.1 对象划分

| 对象 | 含义 |
|---|---|
| `session_id` | OpenCode 对话上下文；正式会话绑定资料域 |
| `run_id` | 一次正式业务任务，具有独立输入、状态、结果和版本 |
| `runtime_id` | 执行任务的账号/资料域运行环境 |
| 现有 `jobs` | 环境开通、更新、暂停和恢复任务 |
| `tool_call_id` / `operation_id` | 一次工具调用及其稳定业务操作标识 |

不将业务任务塞入现有环境管理 `jobs`，也不假定 OpenCode 内部的消息持久化已经提供平台业务任务语义。

## 7.2 建议状态

```text
queued → running → waiting_input / waiting_approval
             │                  │
             └──────────恢复执行┘
             │
             ├→ succeeded
             ├→ partial
             ├→ failed
             ├→ cancelling → cancelled / 待核对
             └→ needs_reconciliation
```

`needs_reconciliation` 表示无法确认某项外部操作是否完成，不允许自动当作失败重做。

`partial` 必须说明哪些数据或操作已完成、哪些失败及能否继续，不得与“全部完成”使用相同展示。

## 7.3 接收、幂等与调度

- 在一个事务中保存任务及待执行意图；持久化完成后才能返回 202。
- 用可靠出站任务记录或等价机制避免“任务写库成功但未派发”的丢单窗口。
- 幂等键按用户/资料域和操作类型限定；同键同输入返回原任务，同键不同输入返回冲突。
- 幂等记录设置明确保留期，且不短于相应操作可重试窗口。
- 任务领取使用租约、心跳、尝试次数和稳定执行标识；过期接管后拒绝旧执行者继续更新状态。
- 对会产生副作用的下游调用，使用稳定 `operation_id` 与下游幂等/核对接口，或明确补偿及人工处置方式。
- 不把所有同参数调用都去重；用户明确发起的新任务应有新的操作身份。

## 7.4 运行、恢复和取消

- 限制单任务步数、总时长、工具调用次数、并发和模型输出预算。
- 记录已完成工具调用与结果引用，恢复时先核对，不自动重做外部写入。
- 不承诺跨外部系统“天然恰好执行一次”；应基于幂等、核对和必要补偿实现可控效果。
- 浏览器断开只影响展示，不应丢失已接收任务；是否继续执行由任务策略决定。
- 取消分别传播到模型生成、当前工具和后台业务任务。
- 当下游操作无法取消时，返回真实状态与已产生结果，不能虚报取消成功。
- 最终成功由代码检查所需调用结果、数据覆盖和输出结构，而非依赖模型总结。

## 7.5 执行器划分

宿主 Worker 继续管理 Docker 和运行环境；业务 Worker 处理导入、查询计算与报告，不得拥有 Docker 权限。

首期允许数据库驱动的后台执行，不要求 Redis 或独立消息中间件。但必须实现持久化、租约、并发控制和重试语义。

## 7.6 交付与验收

交付 Run 表、接口、执行器、OpenCode 适配层、调用记录、幂等和恢复测试。

通过重复点击、请求超时后重试、控制层重启、Worker 中断、模型失败、工具超时、部分成功和取消测试。所有任务均能查询到终态或明确的待核对状态。

# 8. P0-04：结构化导入与数据库迁移

## 8.1 双链路处理

```text
文档问答：上传 → 文本提取 → 来源块 → 有界引用

结构化业务：上传 → 模板/字段确认 → 校验 → 暂存
          → 导入提交 → Dataset 版本 → 受控查询
```

保留现有文档解析器及部分解析拒绝规则，新增结构化导入服务。不得把现有文本提取上限简单调大后宣称完成数据入库。

## 8.2 导入规则

- 模板版本化，字段映射有明确确认结果。
- 编号、电话、账号等标识类字段按字符串保存，并记录原始类型。
- 对源文件已经损失的精度不能“修复猜测”；识别风险并要求核对原始来源。
- 金额使用明确精度的数值类型，时间保留输入格式、时区或时区未知状态。
- 处理必填、非法值、缺失、重复和格式差异，输出可定位的错误行。
- 定义同文件及跨批次重复规则，不能未经确认覆盖历史数据。
- Excel 公式只按受支持的缓存值处理；缺失缓存或其他未提取内容必须标注，禁止静默补算或获取外部链接。
- 使用暂存区或提交机制，避免导入中断后把半批数据标记为完整数据集。
- 明确导入总量与成功、失败、重复、忽略等互斥口径，统计能够对账。

## 8.3 来源与版本

建议每条规范化数据关联：

```text
资料域、数据集、数据集版本
导入批次、源文件 ID 与摘要
工作表、源行号
原始值、规范化值
映射与清洗规则版本
导入时间、操作者
```

原文件、规范化数据及结果使用不同对象保存，避免修改规范化值时破坏原始来源。

## 8.4 查询与数据库

- 插件仅调用语义明确、参数化的查询和计算接口，不向模型开放任意 SQL。
- 默认限制返回规模、分页、执行时长和数据范围；完整结果保存在模型外。
- OpenCode 自有会话库首轮保持现状。
- 控制库在小规模单副本下可以暂留 SQLite，但应拆分读写事务、加入明确迁移和回归。[S05]
- 新增业务数据、Run 和结果采用独立关系型存储；数据库产品以甲方批准及团队运维能力决定。
- 引入 schema 版本、迁移历史、升级前检查、备份要求及失败处理。不能依靠启动时临时补列。

## 8.5 交付与验收

交付数据模型、模板、导入服务、数据集 API、受控查询和迁移脚本。

验收包含精度风险、日期异常、重复导入、缺列、公式缓存缺失、中途退出和迁移失败；任务结果能定位到导入批次与原始行，不完整数据集不会被当成完整数据集计算。

# 9. P0-05：Skill、插件与模型受控发布

## 9.1 官方 Skill 与个人 Skill 分离

| 类型 | 使用边界 |
|---|---|
| 官方业务 Skill | 部门公共 Skill 由超级管理员唯一审核发布、授权和下架；版本不可覆盖，正式任务固定版本，用户主要填写业务参数 |
| 个人辅助 Skill | 用于表达、摘要与辅助整理；不能改变授权、强制校验、审批和结果标准 |

当前选择 Skill 主要向消息加入名称提示，账号环境同时发布全部启用 Skill。正式任务应显式绑定主 Skill 版本及其依赖，不能仅依靠名字提示决定执行合同。[S06][S08]

主 Skill 正文可由后端在启动时明确加载；辅助 Skill 按需读取。但“加载正文”仍不是步骤执行保证，硬性约束必须由程序实现。

## 9.2 建议 Skill 包

```text
business/skills/<skill-id>/
  SKILL.md
  manifest.json
  input.schema.json
  output.schema.json
  tests/
```

以下为**待实现的控制层清单示例**，不是 OpenCode 原生保证支持的字段：

```json
{
  "id": "material-review",
  "version": "1.0.0",
  "required_tools": ["px_dataset_describe", "px_dataset_validate"],
  "input_schema": "input.schema.json",
  "output_schema": "output.schema.json",
  "policy_ref": "material-review-policy-v1"
}
```

清单中的工具依赖、Schema 和策略引用必须由控制层读取、校验和执行。审核、灰度启用、撤回和兼容性检查都需要有实际 API 与测试。审核发布角色固定为超级管理员；本次既有模板权限归属变更不代表这套正式发布流程已完成。

## 9.3 插件与工具合同

插件按业务能力组织，可以包含多个工具。不建议按每一个 HTTP 路由机械创建插件，也不提供通用 `request(url, body)`。

每个工具至少定义：

| 合同 | 要求 |
|---|---|
| 名称和版本 | 使用项目命名空间，检查与原生/其他插件工具冲突 |
| 输入与输出 | 明确 Schema，未知字段拒绝或按合同处理 |
| 权限 | 可操作资料范围、读写属性和审批要求 |
| 资源 | 超时、调用次数、并发、返回行数和字节限制 |
| 可靠性 | 幂等标识、重试条件、取消及核对方式 |
| 网络 | 固定批准服务，不能接受任意 URL 或连接串 |
| 展示 | 面向用户的名称、状态和允许展示字段，禁止透传原始敏感负载 |

插件包发布时验证内容、版本、摘要、兼容性、工具清单和依赖；实际加载导出的工具要与批准清单对应。发布可信可执行代码，不等于允许其访问所有资料。

## 9.4 受控业务接口代理与凭据

现有 Agent 网络仅包含账号内部网络；业务接口接入需新增受控通路，不应直接开放网络。[S09]

业务代理负责验证请求身份和任务映射、核对权限与参数、注入上游凭据、调用批准接口、保存审计、限制返回结果。

当前发布实现会将解密后的插件选项写入加载文件及测试配置，因此高权限总凭据不能继续作为普通插件选项下发。[S09]

模型和业务长期凭据应位于相应代理边界，提供密钥版本、轮换、撤销及恢复方案。任何任务凭据也必须有最小作用域，不能因为有效期短就拥有全库权限。

## 9.5 模型配置与专用 Agent

- 配置专用业务 Agent，收口非业务工具及原生文件访问。
- 模型上下文、输出、工具调用等能力按已验证配置登记，不统一假设所有模型能力相同。
- 固定实际使用的模型标识和参数，限制任务总时长、步数、调用次数及预算。
- 主请求与标题、摘要、压缩等辅助请求使用同一批准的数据出口策略。
- 不自动切换到未经批准的外部模型。
- 版本追溯表示能核对当时配置，不承诺不同时间模型生成内容完全一致。

## 9.6 验收

加载成功不能代替业务验收。每个官方 Skill 用合成数据验证正常、缺参、无数据、部分数据、接口失败、权限不足、取消、重复提交及恶意资料指令场景。

重点检查正确工具调用、范围限制、异常处理、结果来源和完成判定，而不是只评审最后一段回答的文字质量。

# 10. P0-06：结果、审计与人工复核

## 10.1 结果分层

工具同时提供“模型可读投影”和“受控完整结果”，两者不得混为一份无限扩大的输出。

```text
模型可读：摘要、关键指标、覆盖说明、缺失项、result_set_id

完整结果：分页明细、来源、数据版本、报告与附件
          由控制层鉴权后提供给界面或后续受控工具
```

大结果保存在数据库或文件存储中，不依赖模型上下文保全。综合任务引用已保存结果集，而不是把前一段模型总结作为唯一事实输入。

## 10.2 状态与覆盖

工具输出分别表达：

- 执行状态：成功、失败、取消、待核对。
- 数据覆盖：完整、部分、未知。
- 展示状态：全部、分页、摘要或截断。
- 业务结果：有数据或没有符合条件的数据。

这些不是同一维度。接口失败不能等同于空数据；分页预览也不等于全量计算只做了一部分。

## 10.3 来源、报告与复核

- 结果关联任务、Skill、插件、模型配置、数据版本、查询参数和来源记录。
- 正式报告使用受控模板与报告服务生成，不为导出而开放通用 Shell。
- 区分原始事实、程序计算和模型解释，展示不确定性及待核对事项。
- 建立草稿、待复核、已复核、退回状态及复核人、意见和时间。
- 正式导出核验当前权限和审批，记录导出范围、版本及文件摘要。
- 文件下载使用不透明 ID 并校验归属；路径和 ID 难猜都不能替代授权。

## 10.4 审计与日志

审计至少记录操作者、动作、资料范围、任务、工具及版本、审批、结果、拒绝原因和时间。审计与普通诊断日志分开存储和授权。

关键审计采用受限追加或独立存储，明确高权限修改审计的受控运维程序。哈希或签名可以用于完整性核验，但不能单独证明数据内容真实或替代正式证据管理程序。

不得记录密码、API Key、完整认证头或不必要的敏感正文。模型内部推理不属于必须留存的审计数据；记录实际输入引用、外部动作、状态与结果即可。

## 10.5 交付与验收

交付结果集服务、来源查询、前端结果组件、报告模板、复核与导出、审计接口及存储策略。

任一正式报告都能核对发起人、授权范围、输入数据、执行版本、结果来源、审核和导出记录。未授权用户不能通过旧链接或其他任务获取结果。

# 11. P0-07：文件存储与资源配额

## 11.1 配额范围

现有原始上传配额不能覆盖解析文本、成果和 HOME 的全部增长，应新增完整空间管理。[S02][S03]

| 层次 | 需要限制或监测的对象 |
|---|---|
| 单任务 | 上传大小、解包规模、数据行数、处理时间、工具调用次数、结果规模 |
| 单账号/资料域 | 并发任务、原文件、解析结果、成果、缓存及会话相关占用 |
| 整个平台 | 数据库、日志、备份暂存、Docker 数据、磁盘和 inode、系统保留空间 |

配额值根据实际数据和目标服务器压测确定，不把示例值直接写成最终容量承诺。

## 11.2 实现要求

- 上传、解析、报告生成等阶段预留容量，并在失败或取消后释放预留。
- 应用配额与存储层硬限制配合；无法提供硬配额的平台需明确替代隔离和风险处理，不得宣称已具备。
- 缓存、临时文件和可重建中间产物按策略回收，进程重启后能够重新核算。
- 业务原件、已复核成果和审计记录遵循批准的保留与冻结策略，不能因磁盘不足自动删除。
- 使用解析进程资源限制、文件类型和实际内容校验，禁止执行宏或外部链接。
- 对格式解析等不可信输入处理，明确进程、网络、文件权限和挂载范围；资源限额不等于独立文件系统沙箱。

## 11.3 容量规划

现有每账号三容器预算和四个名额只作为历史配置参考，不代表正式并发能力，也不包含新增业务服务或本地模型推理预算。[S11]

按“登录用户数、活跃运行环境数、并发业务任务数、导入规模、模型吞吐、保存年限”分别测量。单账号串行任务也可能产生高磁盘或高计算负载。

## 11.4 验收

大文件、异常压缩包、连续导入、批量报告、磁盘接近阈值、进程中断后残留清理等场景均受控，不影响其他账号的基本可用性，不删除正式资料。

# 12. P0-08：一致性备份与恢复

## 12.1 备份对象

控制数据库、业务数据库、账号 HOME/workspace/files、官方 Skill、插件包、任务和结果、审计、部署与运行配置，以及匹配的密钥版本均纳入方案。

密钥与业务数据分开保护，但必须可以按恢复清单匹配。备份中可能包含真实敏感资料，不能混入普通源码或公开交付包。

## 12.2 一致性与自动化

- 明确恢复点，协调数据库、文件和配置的对应关系。
- 沿用现有暂停写入、离线快照、摘要校验和独立卷验证方式；在线数据库备份仅能解决其自身一致性，不自动覆盖文件与配置。[S11]
- 不把直接复制运行目录视为正式一致性备份。
- 定时执行、校验、记录成功时间，并对失败和超过备份时效告警。
- 使用独立且获批准的存储位置，不只保存在生产同盘。
- 清理、保留和不可变要求由甲方数据制度确定；保留到期与冻结要求需能覆盖到备份生命周期。

## 12.3 RPO / RTO

上线前确认：

- **RPO：** 最多可接受丢失多久的数据。
- **RTO：** 发生故障后最多可接受多久恢复服务。

数值通过合同与演练确定，本文不作未经验证的零丢失或秒恢复承诺。单节点可恢复交付不是高可用交付。

## 12.4 恢复演练

在独立环境恢复数据库、资料、版本和对应密钥，校验用户权限、任务状态、结果来源及代表性文件，再执行一项合成任务。

恢复不得直接覆盖唯一生产卷。对尚未确认的源卷、故障现场及新增数据先保护和留存。

## 12.5 交付与验收

交付备份计划、自动脚本、恢复清单、操作手册、密钥恢复说明及演练报告。

必须证明能从指定恢复点还原可用系统并核对数据关系，而不仅是压缩包可解开或数据库可启动。

# 13. P0-09：监控、发布门禁与上线验收

## 13.1 分层健康检查

| 检查 | 目的 |
|---|---|
| Liveness | 进程是否还能响应；避免将外部模型故障作为无限重启原因 |
| Readiness | 必要配置、数据库及服务条件是否就绪 |
| Capability | Worker、账号 Agent、批准模型和业务接口是否可用，哪些功能受影响 |

当前固定 `/health` 不能证明所有业务依赖健康，应保留简单存活探针并增加必要的就绪和能力检查。[S06]

探针不应访问真实业务资料或频繁调用收费模型。深度验证采用受控合成用例，权限和调用预算单独配置。

## 13.2 P0 最低监控

- CPU、内存、磁盘、inode 和数据库异常。
- 宿主/业务 Worker 心跳、租约异常、任务积压和超时。
- 模型、插件及业务接口持续失败；任务部分完成率和待核对任务。
- 上传、解析和报告失败；备份失败、备份过期和证书到期。
- 认证异常、越权拒绝和高频调用。

告警需明确接收人、处置入口和恢复条件，不能只保存一条无人查看的日志。

## 13.3 诊断关联与脱敏

统一关联 `request_id → run_id → session_id → tool_call_id → runtime_id`。对外提供排查编号和可理解错误，对内记录最小必要诊断信息。

告警、异常堆栈和链路追踪不得默认采集文件正文、模型完整输入、认证头和密钥。

## 13.4 发布门禁

- 每个正式版本固定 Git 提交、验收镜像摘要、前端资产、数据库版本、官方 Skill 和插件版本。
- 不只用 `latest` 或可变标签判断运行内容。
- 执行单元测试、合同测试、权限/隔离测试、迁移、关键 Skill 用例、依赖/镜像与密钥扫描。
- 外网构建到内网交付需保存依赖锁、软件组件清单、镜像核验信息和离线安装验证结果。
- 运行环境不得临时安装未审核依赖。
- 上游 OpenCode 升级与业务功能升级分开验证，维护托管补丁和兼容性测试。

## 13.5 上线与回退

上线前完成目标服务器、实际网络、批准模型和真实接口环境的联调。数据尽量采用专用合成/测试数据；真实资料验证须按甲方审批范围执行。

应用回退与数据库兼容分别设计。若数据迁移不可逆，优先选择兼容迁移、向前修复或独立恢复方案，不能仅换旧镜像就宣布回退完成。

## 13.6 验收

能够主动发现关键故障；生产版本可以核对到完整清单；错误能跨组件定位；发布失败有实际可执行的处置流程。当前单进程缓存和协调机制未改造前，不允许直接通过增加 API worker 数量宣称扩容完成。[S03]

# 14. 数据模型与接口建议

本节是逻辑设计，字段和路径需在实现时通过现有 OpenAPI 合同检查，不是已经存在的接口。

## 14.1 建议新增逻辑实体

| 实体 | 主要内容 |
|---|---|
| `business_scopes` | 案件/任务资料域、状态、负责人及保留策略引用 |
| `scope_members` | 用户、资料域、成员权限及有效状态；不新增平台角色，也不默认开放管理员修改部门归属 |
| `datasets` / `dataset_versions` | 资料范围、导入来源、字段结构、版本和完整性 |
| `import_batches` / `import_errors` | 导入参数、规则版本、行统计及可定位错误 |
| `official_skill_releases` | Skill ID、不可变版本、正文摘要、合同、依赖、审核及发布状态；审核/发布/授权/下架主体必须为超级管理员 |
| `business_runs` | 输入引用、身份、范围、版本快照、状态和结果 |
| `run_events` | 任务级序号、事件类型、脱敏负载与时间 |
| `run_dispatch` / `run_attempts` | 派发意图、租约、执行者、心跳、尝试和失败分类 |
| `tool_invocations` | 工具版本、稳定操作 ID、参数摘要、状态及下游任务引用 |
| `approvals` | 审批主体、操作和参数绑定、有效期、结果 |
| `result_sets` / `artifacts` | 数据覆盖、来源、文件引用及生成版本 |
| `reviews` | 复核人、结论、意见、结果版本和时间 |
| `audit_events` | 受控操作及拒绝记录，受限访问和追加策略 |

不把所有实体直接塞入 OpenCode 内部数据库。授权、业务元数据和控制元数据的存储位置应在详细设计时明确，跨库更新使用可恢复事务边界，不假定天然原子。

### 三角色的账号与认证合同

现有 users.role 取值限定为 `super_admin/admin/user`，平台角色不保存在客户端可修改的普通配置里。认证结果增加服务端生成的 capabilities；前端可据此显示入口，但每个 API 仍重新验证角色、当前账号状态和目标资源。

沿用现有管理 API 前缀，不为角色变化重命名全部接口：

| 合同 | 超级管理员 | 管理员 | 普通用户 |
|---|---|---|---|
| POST /admin/users | 可创建 user 或 admin；不能创建 super_admin | 仅创建 user；默认 user | 拒绝 |
| PATCH /admin/users/{uid} 与 reset-password | 可管理 user/admin 的启停及重置，按目标类型限制授权字段；禁止操作 super_admin | 只能管理 user；仅模型授权，不接受 plugin_ids | 拒绝 |
| /admin/models 及连接测试 | 按现有模型接口管理与授权 | 同左 | 拒绝 |
| /admin/plugins、/admin/templates | 独占平台管理 | 拒绝 | 拒绝 |
| /admin/users/{uid}/runtime/*、/admin/jobs | 独占环境维护，仅适用普通用户运行环境 | 拒绝 | 拒绝 |
| /admin/audit | 只读脱敏管理审计 | 只读脱敏管理审计 | 拒绝 |
| /skills、/plugins 等个人业务接口 | 拒绝 | 拒绝 | 保留现有本人范围能力 |
| /me/password、本人令牌 | 本人自助管理 | 本人自助管理 | 本人自助管理 |

创建 admin 时只接收账号、密码和 role，不接受模型/插件授权字段，不创建 runtime/jobs/卷。管理员创建或编辑 user 不得携带 plugin_ids，连空列表也不作为“无操作”放行；现有客户端需省略无权字段。PATCH 不支持角色变更。普通账号管理接口不能修改超级管理员，超级管理员自身使用自助改密。

审计对外使用受控字段与稳定结果 `success/denied/failed`，不返回凭据、私有路径、原始业务正文或任意内部负载；实际字段以本分支生成的 OpenAPI 为准。模型删除等尚无接口的能力不能因“三角色”描述自动视作已完成，现有停用功能继续保留。

## 14.2 Run 最小信息

```text
身份：id、created_by、scope_id、session_id、runtime_id
输入：input_json、input_digest、dataset_version_refs
版本：skill_release_ref、plugin_versions、model_config_snapshot
状态：status、state_version、error_code、result_refs
时间：created_at、started_at、updated_at、finished_at
控制：idempotency_key、cancel_requested_at、policy_snapshot_ref
```

`policy_snapshot_ref` 用于追溯当时决策，不替代执行时检查最新撤权。实际密钥不进入版本快照、任务正文或审计负载。

## 14.3 建议 API 前缀

保留现有 `/api/console/v1`。新增业务接口可统一置于 `/api/console/v1/business`，管理发布接口继续置于管理路由。不要在本轮同时重命名现有全部 API。

| 方法 | 建议路径（相对业务前缀） | 作用 |
|---|---|---|
| GET | `/scopes` | 返回当前身份可访问的资料域 |
| GET | `/skills` | 当前范围内可用的官方 Skill 版本 |
| POST | `/imports` | 基于已上传文件发起结构化导入 |
| GET | `/imports/{id}` | 导入状态、统计及错误报告 |
| GET | `/datasets/{id}` | 数据集元信息和允许访问的版本 |
| POST | `/runs` | 校验后持久化并接收任务 |
| GET | `/runs/{id}` | 查询状态、版本和结果引用 |
| GET | `/runs/{id}/events?after={sequence}` | 有权访问的任务事件；支持明确的保留窗口 |
| POST | `/runs/{id}/input` | 补充参数，并重新校验受影响约束 |
| POST | `/runs/{id}/cancel` | 请求取消，返回真实取消状态 |
| POST | `/runs/{id}/approvals/{approval_id}` | 提交与具体操作绑定的审批 |
| GET | `/results/{id}` | 结果摘要、覆盖说明和来源 |
| GET | `/results/{id}/rows` | 受限分页数据 |
| POST | `/results/{id}/reviews` | 记录人工复核 |
| POST | `/results/{id}/exports` | 发起经授权导出 |
| GET | `/artifacts/{id}/download` | 鉴权下载成果 |

事件持久化只针对业务任务和必要工具状态，不要求逐 Token 保存模型流。超出事件保留窗口时，客户端先刷新任务快照，不默默假装完整重放。

## 14.4 任务创建示例

以下 ID 均为合成示例；请求不允许选择身份、容器、原生文件路径、模型地址或凭据。

```json
{
  "scope_id": "scope_demo",
  "skill_release": {"id": "material-review", "version": "1.0.0"},
  "dataset_versions": ["dataset_version_demo"],
  "parameters": {"output_format": "summary"}
}
```

请求头携带幂等键。服务端应先确认范围、正式版本和参数，再生成可信运行上下文。

返回 202：

```json
{
  "run_id": "run_demo",
  "status": "queued",
  "accepted": true
}
```

此时只能表示已持久化接收，不能表示业务成功。

## 14.5 统一错误语义

```text
401：认证无效
403：认证有效但不允许该操作
404：资源不存在或按防枚举策略不可见
409：状态冲突、同幂等键不同输入或版本冲突
413：请求或引用规模超出上限
422：参数/数据不符合业务合同
429：调用或资源配额受限
503：必要能力暂不可用
```

错误体至少包含稳定业务错误码、可理解提示和 `request_id`。后台任务失败通过 Run 状态表达，不以一次 HTTP 成功响应掩盖。

| B：资料域与授权 | 已确定三角色的 API 和导航约束；后续资料域、会话绑定与资源鉴权 | 管理员所有禁区、超级管理员目标保护、管理账号无 runtime 及跨域/撤权测试通过 |
| C：任务执行基础 | Run、幂等、派发、租约、取消和恢复；先接合成工具 | 重复提交、重启和未知外部操作核对测试通过 |
| D：官方能力发布 | 超级管理员唯一审核部门公共 Skill；发布授权下架、版本固定、工具合同、专用 Agent 与业务代理 | 审核身份、状态转换、加载清单、授权、凭据隔离和恶意输入测试通过；不得以既有模板管理代替 |
| E：数据和结果闭环 | Excel 导入、数据集、受控查询、结果、复核与导出 | 行统计可对账，来源可追溯，失败不误报完成 |
| F：生产保障 | 完整配额、监控、自动备份、恢复和离线发布 | 容量边界、告警、独立恢复及升级演练通过 |
| G：目标环境验收 | 内网联调、批准模型与业务接口、持续负载、最终交付清单 | 所有 P0 门槛通过或按风险明确禁止上线 |

部署安全、审计和备份设计应从批次 A 开始，不留到代码完成后临时补齐；批次 F 是完成集成验证，不是首次考虑这些问题。

### 本次三角色增量与后续边界

本次增量只实施三角色权限、能力导航、现有模板/插件管理归属、角色 schema 迁移及对应保护。暂不建设部门组织编辑，不给 admin 独立运行环境维护权，不提供角色升降级，也不实现正式部门公共 Skill 审核状态机。旧普通用户个人 Skill 与已授权插件配置必须回归保留。

控制镜像使用独立标签 `peixian-control:console-r2-roles`，保留旧 r1；保留镜像不意味着旧镜像可以直接打开新 schema。Windows up/start 和 Linux 启动流程均先执行兼容检查，再以该次返回的不可变 image_id 启动，避免校验后标签竞态。部署迁移、合成 API/UI 以及既有账号数据回归各自记录结果，未执行的层次明确写待验证。

## 16.3 每批提交必带材料

提交说明应包含：解决的问题、修改范围、接口和数据变化、已执行的测试、跳过及未验证项、回退或兼容影响。

无法在当前环境执行的 Docker、模型或内网测试，应明确记录“待目标环境验证”，不得用类型检查、Mock 测试或 HTTP 202 代替真实完成。

## 16.4 第一条验证闭环

优先选择容易核对、无需复杂业务判断的合成资料任务：

```text
上传合成 Excel → 映射与校验 → 提交数据集版本
→ 创建固定官方 Skill 的 Run → 调用受控校验/查询工具
→ 保存结构化结果 → 展示来源 → 人工复核 → 导出报告
```

先验证整条可靠性与权限链，再逐项接入更复杂业务。不要在基础合同尚未稳定时同时铺开全部分析功能。

| 编号 | 测试场景 | 必须观察到的结果 |

| RUN-06 | 部分工具成功后失败 | 标记部分完成/失败并保留已产生结果 |
| DATA-01 | 格式、精度或时间异常 | 定位错误，拒绝猜测修复 |
| DATA-02 | 重复导入、中途终止 | 数据版本和行统计一致，不出现假完整批次 |

# 18. P0 边界、后续升级与待确认事项

## 18.1 不默认纳入本轮

通用 SaaS 多租户、完整组织人事系统、可视化工作流、开放插件市场、复杂多 Agent 调度、Kubernetes、跨机房容灾和大型统一运营平台不作为本轮默认建设目标。

Redis、对象存储、多节点和数据库集群是可能的实现手段，不是“正式版”三个字必然要求的组件。

SSO、特定数据库/操作系统适配、高可用或专项测评若已写入甲方要求，则应提前纳入 P0。

## 18.2 后续升级方向

P1 可围绕实际使用完善统一认证、运营界面、Skill 开发工具、更多导入模板和业务能力。

P2 再按负载与可用性目标推进共享缓存/事件、运行节点注册、资源调度、多副本与高可用。不得仅增加控制层进程数量而忽略当前进程内缓存、登录限流和流式协调状态。[S03]

## 18.3 开发前需要确认的事项

| 事项 | 影响 |
|---|---|
| 实际上线人数、并发任务与资料规模 | 配额、调度、存储和性能验收 |
| 目标服务器、CPU 架构、操作系统及网络 | 镜像构建、服务安装、离线交付与兼容性 |
| 模型部署位置、协议和获批准的数据范围 | Relay、模型能力、数据出口及回归 |
| 真实业务接口清单、鉴权、限流和取消能力 | 插件合同、凭据代理和幂等策略 |
| 是否多人协作同一案件/资料域 | 成员关系与共享数据权限；不改变已确定的三平台角色 |
| 是否要求同账号跨案件硬隔离 | Runtime 分配、文件挂载和任务调度 |
| 数据保留、冻结、删除与审计要求 | 存储、清理、备份和审计生命周期 |
| RPO、RTO 与可用性目标 | 单机恢复或高可用范围 |
| SSO、数据库和安全测评约束 | P0 范围及验收标准 |
| 生产版本维护和告警接收负责人 | 发布、值守、故障处置和长期运维 |

### TBD09：公共 Skill 审核与角色边界

**已决定部分，不再作为开放选项：** 平台仅有 super_admin/admin/user；部门公共 Skill 的审核、发布、授权与下架唯一归超级管理员。管理员不能管理平台插件或公共模板，不能修改部门组织与归属，不能独立维护运行环境；普通用户保留个人 Skill 与获授权插件的个人配置。

**仍待批次 D 详细设计的部分：** 公共 Skill 的提交流程、状态机、审核意见与退回、版本和依赖合同、授权目标及生效撤回规则。这些是流程实现问题，不再讨论增加审核角色。本次现有模板管理归属变更不构成 TBD09 全部关闭，也不构成审核发布验收通过。

这些信息用于确定实现和验收边界；未具备真实接口时，可以先用合成插件完成基础开发，不应因此伪造实际接口已验证的结论。

## 18.4 最终交付包

建议最终交付包含源代码与提交记录、固定镜像及摘要、数据库迁移、官方 Skill 与插件包、生产配置模板、安装/升级脚本、操作手册、权限矩阵、测试报告、备份恢复报告和已知限制。

密码、密钥、真实业务数据和包含敏感内容的备份，通过独立批准渠道交接，不进入公开 Git 仓库、镜像或普通交付压缩包。

## 18.5 最终结论

本次升级的核心不是把 MVP 变成庞大的平台，而是补齐正式使用必须具备的边界：

> 每项任务都知道谁发起、获准访问什么、使用了什么数据和能力版本、实际执行了什么、产生了哪些可核对结果；遇到错误不会误报完成，遇到故障能够定位、停止和恢复。

在这个基础上，OpenCode 继续承担灵活执行内核的角色，Skill 组织业务方法，插件连接受控能力，确定性的权限、计算、状态和审计由程序负责。
