# 第一轮稳定性加固验收报告

日期：2026-09-16。基线：`dff944188605ff65a681409423347fcb57066501`。开发分支：`codex/concurrency-hardening`。最终源码 SHA 与交付校验值以包内 `release-manifest.json` 为准。

## 结论

源码加固、自动化回归、真实浏览器基本检查和短时控制层 50 合成账号负载已经完成。**50 个真实 Agent / Gateway / Relay 环境、真实模型／内网接口、目标服务器及四小时稳定性仍未验收。** 当前交付是源码、部署工具、依赖及脱敏证据包；没有把旧镜像或测试桩当作新镜像及真实推理结果。

没有修改原部署的配置、用户、数据卷或会话，没有推送远端。浏览器测试使用独立回环端口 19490、临时 SQLite 和合成账号；压测使用系统分配的其他空闲回环端口。

## 一、完成的代码

- 配置 v2 与旧 v1 兼容、最多 64 个环境的配置边界、独立 50 人示例、统一 CPU/RAM 预算、网络容量预检、镜像配置能力检查。
- SQLite 只读连接与短快照、WAL 初始化分离、全异常路径清理、写锁等待上限。
- DB 与密码有界工作池、取消不提前释放运行线程、关停不再执行排队工作、密码计算移出事务。
- 登录和改密竞态核验、被撤销签发者不能生成新令牌、管理员密码计算期间失去身份后不再创建账号或重置密码。
- 新的线程并发下，技能、插件、模型及模板更新在事务内读取旧值、合并与写入，避免覆盖不同字段或丢失回退历史。
- SSE/普通 HTTP/下载分池；viewer、owner、上游连接分别限额；响应生命周期清理、准备态超时、慢客户端身份撤销、身份复核错峰。
- 同一次请求的鉴权与环境查询合并，环境绑定只保存在本请求，不跨请求缓存身份。
- fetch SSE、状态码与 Retry-After、重连只读补齐、资源级刷新、单在途合并、隐藏页降频、草稿保留及旧响应防覆盖。
- OpenAPI、Python 示例、部署及验收工具、版本化配置回退保护、精确镜像选择打包和明确无镜像的源码打包模式。

后端有两条已有 Starlette/httpx/AnyIO 弃用提示，不是测试失败。Linux 原语检查包括固定目录句柄抵抗符号链接替换、解析进程 rlimit、FIFO 拒绝；应在目标 Linux 镜像补跑。

真实浏览器曾发现默认时钟直接引用 `setTimeout` 后作为对象方法调用，导致 `Illegal invocation`，进而使 onOpen 回调异常、SSE 未开始读取的正文没有释放。已改为包装函数并补充正文 finally 取消，新增两项回归；修复后重新构建并在浏览器重测。这说明单元测试与真实浏览器检查均有必要。

## 三、控制层分级压测

最终报告：[control-load-request-binding-20260916.json](../benchmarks/control-load-request-binding-20260916.json)。总时长 **124.25 秒**，10→20→35→50 账号各 30 秒。

测试环境为 Windows、Python 3.12.14，本机可见 20 个逻辑 CPU。客户端和服务端在同一 Python 进程事件循环，使用真实 Uvicorn 和回环 TCP；不是目标 16 核服务器，也没有把 Control 限在候选容器的 2 CPU/2 GiB 内。因此这些数字只能证明该合成控制层场景。

| 项目 | 最终结果 |
|---|---:|
| 各阶段 SSE | 20 / 40 / 70 / 100 |
| SSE 提前关闭、资源拒绝 | 0 / 0 |
| 峰值合成活跃生成 | 50 |
| 峰值 viewer / 上游流 / owner | 100 / 100 / 50 |
| 实际客户端 HTTP 同时在途峰值 | 49 |
| DB 工作与等待合计峰值 | 26（上限仍为 8 + 32） |
| 接收事件总数 | 28,716 |
| 串账号事件 / 无效事件 | 0 / 0 |
| 令牌撤销后旧流关闭 | 0.969 秒；当时其他 49 账号继续读取 |
| 撤销后的新请求 / 跨账号会话访问 | 401 / 404 |
| 结束后的 viewer、上游、owner、下载、准备态 | 全部为 0 |

50 账号阶段完整 HTTP 响应耗时：

| 接口 | 请求数 | p95 | p99 |
|---|---:|---:|---:|
| health | 301 | 403.60 ms | 767.83 ms |
| me | 300 | 377.48 ms | 923.73 ms |
| messages | 2,857 | 460.65 ms | 909.41 ms |
| sessions | 750 | 427.49 ms | 779.26 ms |

所有采样接口返回 200，达到 p95≤500ms、p99≤1500ms。曾有一条 health 请求耗时 **2423.42ms**，50 账号时的 p95 也接近门槛，应继续长稳态和故障测试，不把短测结果扩大为持续服务承诺。

保留了修复前的失败证据：

- [首次阶段失败](../benchmarks/control-load-smoke-20260916.json)：35 账号准入阶段 DB 队列达到 40，订阅不足。
- [仅身份错峰后的失败](../benchmarks/control-load-phase-fixed-20260916.json)：50 账号曾达到 100 SSE，随后 28 流提前关闭，DB 拒绝 148 次。
- [两账号冒烟](../benchmarks/control-load-two-account-20260916.json)：用于确认工具与撤销检查能够正常执行。

最终通过的改变是减少重复查询，而非增加线程、队列或降低负载。普通消息请求由鉴权、重复环境查询和过滤等多次 offload，减少为鉴权环境联合读取与消息过滤；请求仍各自验证身份。测试参数和指标门槛保留在各 JSON 中。

## 四、容量和 Docker 阻断

配置示例没有填写未经测量的低内存配额。沿用旧账号容器上限，50 组要求 **137.25 GiB RAM、41.5 个 CPU 规划核**，16 核/32 GiB 必须被预检拒绝。该计算是容器 cap 的严格规划，不是实际 RSS 峰值。

本机尝试启动 Docker Desktop，但后台在 2026-09-16 15:52:30 报 `initializing Ingest server`，无法把 `sailor-ingest.sock` 转为 `.stale`，错误为 `The file cannot be accessed by the system`，随后关闭；15:53:18 有退出记录。Linux 引擎管道未建立。仅结束了本次空等的启动命令，没有清理 socket、重置 Docker、修改地址池或删除卷。

因此本轮真实运行环境采样数量为 **0**，新的真实 Agent 同时活动任务数量为 **0**。无法据此确定可靠的新账号内存配额；也不能给出本机实际容纳多少组环境的实测结论。
