# 远端受限环境验证：两账号画像与 50 账号容量门槛

日期：2026-09-16。分支：`codex/concurrency-hardening`。

## 1. 结论

**两账号真实 DeepSeek 对话、合成插件调用、TXT/DOCX 解析、HTTPS 与事件订阅通过；当前镜像和既定容量契约未满足 16 CPU／32 GiB 下 50 个独立常驻账号环境的前置门槛。** 因此未扩大创建至 10／20／35／50 组，也未执行 50 路任务、100 条订阅及四小时稳定性测试。

这里的限制是本轮实测画像与既定硬配额预算之间的冲突，不是宣布 OpenCode 在所有配置下都无法支持 50 人。后续必须降低实际资源占用并重新验证，或者调整服务器资源；不能取消内存准入检查，或直接把 Agent 限额设到已观测峰值以下后宣称通过。

机器可读证据及原始报告校验值见 [remote-profile-20260916.json](evidence/remote-profile-20260916.json)。本报告补充 [第一轮稳定性加固报告](HARDENING_R1_REPORT.md)，不改变其中历史测试发生时的状态。

## 2. 版本与隔离边界

- 上传代码基线：`64bcd2dbb6f3739678d91fdaa5f963b0edeab49d`；应用镜像源码标签为 `e93b7af95c0dae9752cbfb3d63449306fb78056e`，两者之间为文档修改。

- 实际宿主为 BigCloud Enterprise Linux V25.0.1 LTS，x86_64，32 个逻辑 CPU、约 251 GiB 内存，Docker 25.0.3、Compose 2.24.0、cgroup v1/cgroupfs，无 swap。不是独占的 16 CPU／32 GiB 物理机，也不是 Ubuntu 24.04 安装验收。
- 独立部署标识 `loadtest-r1-20260916`，数据根位于 `/data/agent-loadtest-r1-20260916`。原上传仓库未更改；使用该目录中的独立 worktree、网络、控制卷、账号卷和私密凭据。
- 两个合成普通账号各使用 Agent、Gateway、Relay 三个容器，另有 Control 和 HTTPS，共 8 个容器。入口仅为宿主回环 `https://127.0.0.1:19443`，内部 Control 为 `127.0.0.1:14094`。
- 共用测试父组：CPU quota 16，cpuset `16-31`，应用内存与 memory+swap 上限均为 **28 GiB**；另计 **4 GiB** 宿主／平台规划余量。容量检查采用实际资源与 16 CPU／32 GiB 的较小值，没有借用大宿主的剩余内存通过准入。
- 已通过实际 `/proc/<pid>/cgroup` 检查，确认所有 8 个容器的 CPU、cpuacct、memory、cpuset、pids 控制器均位于绝对测试父组下。Worker 也加入测试父组。
- Docker 守护进程、宿主探针与压测客户端位于父组外；合成接口位于父组外，模拟独立的接口服务；DeepSeek 在外部提供推理。4 GiB 是核算余量，不是另一块独占硬隔离区域。`docker exec` 采样进程在被采样容器内，会产生少量观测开销。

准备阶段发现 Docker/containerd 会把相对 `cgroup_parent` 解析到自身服务子树中。已在模型测试前停止并重新创建本次测试容器，改为绝对父组，并逐控制器审计。修正之前的准备数据不计作受限负载证据。本文“启动峰值”为重新创建容器、挂载本次已准备卷后的生命周期峰值，不能替代全新空卷离线冷启动验收。

## 5. 50 账号容量门槛

统一配置下每个 Agent／Gateway／Relay 的内存参数至少为 128 MiB。本轮保留 Control 2 GiB 和规划余量 4 GiB，则：

```text
32 GiB - 4 GiB 余量 - 2 GiB Control = 26624 MiB
26624 / 50 = 532.48 MiB / 账号组三容器
整数统一配额最多 532 MiB / 组
Gateway 128 + Relay 128 后，Agent 最多 276 MiB
```

**276 MiB 低于实际 Agent 的约 454 MiB 峰值。** 因此没有一个经过本轮功能画像支持、并留有额外内存空间的统一候选配额可以直接填入 50 账号／32 GiB 配置。

即使仅把观测峰值向上取整为 454 MiB，Gateway／Relay 都取配置最小值，不给 Agent 增加任何余量，算术预算仍为：

```text
50 × (454 + 128 + 128) + 2048 + 4096
= 41644 MiB ≈ 40.67 GiB
```

这比 32 GiB 多约 **8.67 GiB**，而且尚不是推荐配额或经缩容回归验证的最低配置。峰值受输入、模型、运行时间、解析任务和内存回收策略影响；本轮没有把 40.67 GiB 当成生产内存建议。

原始较高配额为每组 2048＋512＋128 MiB，50 组总预算为 **137.25 GiB**。在 32 GiB 下此配额的内存准入上限是 9 组；第 10 组需要 32.25 GiB。9 是预算数量，未实测 9 路任务。

CPU 也保留原始准入约束。共享系数 4、规划预留 4 时，原每组 3 CPU cap 对应 50 组的规划需求为 **41.5 CPU**，大于 16。若保持此共享系数，50 组的单组 CPU cap 合计需不超过 0.96 CPU；这种低 CPU 配额尚未回归，不能只改数字声称可用。

网络池只读预检通过：50 账号加前端需 151 个 `/28`，已有 7 个专属网段、4089 个可用网段，剩余需求 144。**没有真实创建 150 个账号网络，也没有验证 Control 连接 50 个管理网后的运行表现。**
